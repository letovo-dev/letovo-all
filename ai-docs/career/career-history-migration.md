# Миграция истории карьеры

## Цель

Хранить и показывать в личном кабинете фактические периоды работы пользователя: отдел, одну или несколько должностей, бригаду и навыки на момент перехода.

## Задачи

- [ ] Зафиксировать контракт `career_period` и подтвердить правила: одна активная основная должность, несколько должностей в периоде допустимы. → Проверка: согласован JSON примера из `career-history-source-data.md`.
- [ ] Добавить миграцию с таблицами `user_career_periods` (период, пользователь, отдел, бригада, даты) и `user_career_positions` (роль в периоде, порядок отображения); добавить внешние ключи и запрет двух пересекающихся активных основных периодов. → Проверка: миграция накатывается на чистую БД и откатывается без потери существующих таблиц.
- [ ] Реализовать импорт проверенных исторических данных в новые таблицы; не пытаться вывести даты из `useroles` или `user_achivements`. → Проверка: отчёт импорта содержит число созданных периодов, позиций, отклонённых строк и причины.
- [ ] Изменить операции назначения роли/перевода: одной транзакцией закрывать прежний период, открывать новый, обновлять `user.role`; поддержать добавление второй должности в тот же период. → Проверка: тест создаёт переход и получает корректные `started_at`, `ended_at` и текущую роль.
- [ ] Добавить `GET /user/career/:username`, возвращающий периоды от нового к старому с отделом, бригадой, упорядоченными должностями и навыками; пустая история должна возвращать `200` и пустой массив. → Проверка: контрактный тест покрывает пользователя без истории, с одним периодом и с двумя должностями.
- [ ] Связать навыки с карьерным периодом: в ответе вычислять «новые» относительно предыдущих периодов, а не относительно произвольной даты достижения. → Проверка: тестовый пользователь видит навык новым лишь в первом периоде, где он был получен.
- [ ] Перевести блок «Карьера» в `frontend/src/pages_fsd/user-page/UserPage26.tsx` на новый API, вывести все должности вместо единственного `role` и показать состояние без истории. → Проверка: мобильный и desktop-экран соответствуют карточкам из дизайна для одного и нескольких периодов.
- [ ] Вывести тот же read-only блок на публичной странице профиля либо явно исключить его из продукта в UI-требованиях. → Проверка: решение закреплено e2e-тестом для `/user/:username` и, если применимо, `/profile/:username`.
- [ ] Выполнить миграцию на staging, сверить количество строк с исходной выгрузкой, затем провести production rollout с резервной копией и журналом ошибок. → Проверка: выборка нового API для контрольных пользователей совпадает с утверждёнными исходными данными.
- [ ] Прогнать миграционные, backend-контрактные, frontend-компонентные и e2e-тесты; вручную проверить историю контрольного пользователя. → Проверка: CI зелёный, `ya-yara` одобрила PR.

## Готово, когда

- [ ] Прошлые и текущие карьерные периоды выдаются из отдельной временной модели, а не восстанавливаются эвристикой из достижений.
- [ ] Карточка из дизайна показывает отдел, все должности периода, главу/год и корректный набор новых/предыдущих навыков.
- [ ] Импорт воспроизводим: исходная выгрузка, отчёт валидации и результат миграции можно сверить построчно.

## Примечание

Критический путь: сначала утверждение исходных данных и схема БД, затем импорт и API, после этого frontend. Существующие `useroles` можно оставить как совместимый список назначенных ролей, а `user.role` — как быстрый указатель текущей основной должности.
