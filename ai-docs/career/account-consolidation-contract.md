# Контракт объединения дублирующихся аккаунтов

Этот контракт применяется только к явно переданным строкам `account_merges`. Совпадение ФИО само по себе никогда не запускает объединение. В каждой группе один `canonical_username` — последний аккаунт, который остаётся активным; каждый `source_username` уникален и не может быть каноничным в другой группе.

## Допуск и dry-run

До любой записи импорт валидирует существование всех аккаунтов, единый `canonical_username` в группе, уникальность источников, ФИО и отсутствие пересечений объединённой карьерной истории. Одновременные должности допустимы только в одном периоде и одном отделе. Роль из другого отдела без последовательных дат — причина поместить всю группу в карантин; её нельзя перенести «как есть».

Dry-run не меняет БД и для каждой группы выдаёт: аккаунты, причину допуска или карантина, число строк по каждой таблице до/после/дубликатов, баланс каждого аккаунта и сумму до/после. Его результат вместе с хешем входного файла утверждается до запуска.

## Правила переноса

| Данные | Действие и правило коллизии |
| --- | --- |
| `user.balance` | Перевести сумму балансов всех источников на каноничный аккаунт; у каждого источника установить `0`. Сумма по группе до и после должна совпасть точно. |
| `user_achivements` | Объединить по `(username, achivement_id)`: при конфликте оставить одну запись каноничного аккаунта, `stage` взять максимальный, `datetime` — минимальный, `new` — `false`, если хотя бы в одной записи оно `false`; удалить строку источника. |
| `useroles` и новая карьерная модель (`user_career_periods`, `user_career_positions`, `user_career_skills`) | Перенести на каноничный аккаунт, дедуплицировать одинаковую роль; импортировать карьерные периоды только после проверки единой непересекающейся шкалы. Конфликт — карантин всей группы. Текущую основную роль задаёт подтверждённый последний период, а не произвольная роль источника. |
| `user_brigades`, `user_posts` | Перенести на каноничный аккаунт; при появлении уникального ключа применить правило «каноничная строка побеждает, источник удаляется». |
| `user_likes` | Объединить по уникальному `(username, post_id)`; при конфликте сохранить значение каноничного аккаунта, строку источника удалить. |
| `favourite_posts`, `user_saved` | Объединить по `post_id`; дубликат на каноничном аккаунте оставить, строку источника удалить. Для `favourite_posts` это соответствует уникальному ключу `(post_id, username)`; перед записью для `user_saved` выполняется явная дедупликация. |
| `role` | Права источника удалить; права не объединять, чтобы не выдать дополнительные административные полномочия. Права каноничного аккаунта остаются без изменений. |

## Историческое происхождение и очистка источника

Финансовые и коммуникационные записи не переписываются: `transactions` (sender/receiver), `direct_message`, `usermessage`, `pool`, `usertogroup`, `comments`, `post_reveal_tokens`, `user_activity_daily`, `user_activity_events`, `user_activity_last_seen` сохраняют исходный идентификатор как историческое происхождение. Кабинет и административная сверка находят их через журнал объединения, а не через подмену автора или участника транзакции.

Сессии и доступ источника отзываются: удаляются `cookies`, `user_sessions`, `ws_session` и `chat_override`; действующие права из `role` удаляются. Саму строку пользователя удалять нельзя, пока на неё ссылаются исторические записи: она становится деактивированным техническим tombstone с нулевым балансом, пустыми текущими должностями, бригадой и карьерной историей и без возможности войти. Таким образом, в старом аккаунте не остаётся доступных пользователю денег, достижений, должностей, карьеры, сессий или прав, а неизменяемый аудит не теряет автора.

Перед реализацией миграция обязана сформировать и утвердить инвентарь всех столбцов, ссылающихся на `username` или `userid`, из фактической схемы. Любая неописанная ссылка блокирует запуск, пока для неё не будет добавлено правило: перенос, дедупликация, сохранение исторического происхождения или отзыв.

## Идемпотентность, аудит и восстановление

Для каждой строки источника создаётся `account_merge_ledger` с уникальным `source_username`: идентификаторы и ФИО группы, каноничный и исходный аккаунты, хеш утверждённого входа, автор утверждения, время, статус (`preview`, `applied`, `rolled_back`, `failed`), балансы до/после, счётчики по таблицам и ссылку на снимок до изменения. Повтор того же запуска читает журнал и не прибавляет баланс или данные второй раз; запуск с другим хешем или уже обработанным источником завершается ошибкой.

Применение каждой группы выполняется в одной транзакции с блокировкой всех её аккаунтов. Ошибка до commit откатывает всё. До применения сохраняется защищённый снимок изменяемых строк и отчёт dry-run. Команда rollback по `merge_group_id` может восстановить снимок только если после объединения не было последующих изменений затронутых данных; иначе операция останавливается, создаёт отчёт расхождений и требует ручного утверждения восстановления. В журнале фиксируются как успешное объединение, так и откат.
