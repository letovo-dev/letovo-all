# Аудит ролей доступа (issue #182)

В системе используются две независимые модели, и форма создания аккаунта теперь показывает их отдельно:

- roles — должность в департаменте, ранг и выплата. Значения загружаются из API, а не зашиваются во frontend.
- user.userrights, role и user.chattable — уровень и отдельные права доступа.

Каталог формы покрывает уровни user, child, author, public_author, moder, admin и права write_posts, admin, moder, main_page, whireable, ava_upload, chattable. Для каждого значения показано русское название и назначение; повышенные и устаревшие уровни отмечены явно. Уровень userrights и одноимённые флаги role остаются разными контролями: например, для полного административного доступа нужно осознанно назначить и уровень admin, и право admin.

На проверенном production-снимке было 48 должностей и не было дублей по (rolename, departmentid, rang, payment). Роли «Взломщик сайтов» (45) и «НАРУШИТЕЛЬ» (46) не были назначены. Это кандидаты на бизнес-проверку, но не на автоматическое удаление: исторические ссылки необходимо сохранить. Миграция roles_natural_key_migration.sql только защищает естественный ключ и выводит read-only отчёт по текущим и историческим назначениям.

Детским аккаунтам личная загрузка аватара запрещена существующей политикой. Для остальных аккаунтов администратор явно выбирает право ava_upload; выбранный файл проверяется по MIME и размеру, загружается в namespace нового пользователя и считается установленным только после успешного /user/set_avatar.
