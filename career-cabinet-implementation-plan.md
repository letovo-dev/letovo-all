# Полная реализация раздела «Карьера»

## Цель

Личный кабинет работает как в дизайне: показывает текущую и прошлые карьерные позиции, раскрывает сведения периода и навыки, а кнопка дерева прокачки открывает рабочее представление.

## Задачи

- [ ] Зафиксировать API-контракт `career_period`: `id`, период, отдел, бригада, отсортированные `positions`, навыки и ссылка дерева; подтвердить правило одной основной и нескольких дополнительных должностей. → Проверка: в API-документации есть JSON пустой, текущей и прошлой карточки.
- [ ] Добавить миграцию с `user_career_periods`, `user_career_positions` и привязкой навыков к периоду; создать индексы, внешние ключи и запрет пересечений у основной позиции. → Проверка: миграция накатывается на чистую БД и откатывается без изменения действующих `user`, `roles`, `useroles`.
- [ ] Написать валидатор и dry-run импорт трёх файлов из `career-history-source-data.md`; в apply-режиме записывать периоды, должности и навыки в одной транзакции на пользователя. → Проверка: отчёт содержит созданные записи, неизвестные справочники, дубликаты и пересечения; повторный запуск не создаёт дублей.
- [ ] Перевести backend-операции назначения роли, перевода отдела и добавления второй должности на новую модель: закрывать старый период, открывать/дополнять новый и синхронно обновлять `user.role`. → Проверка: интеграционный тест проверяет повышение, перевод, вторую должность и неизменность истории.
- [ ] Реализовать защищённые административные API создания, изменения и закрытия карьерного периода; ошибки валидации должны быть `4xx`, а не `502`. → Проверка: контрактные тесты покрывают права, некорректные даты, неизвестную роль и конфликт активных позиций.
- [ ] Реализовать публичный `GET /user/career/:username`: сортировка от текущего к прошлому, глава/год по календарю или данным импорта, все должности, бригада, статусы навыков; вернуть `200` и `[]` при отсутствии истории. Старый `/achivements/user/departments/:username` оставить только для обратной совместимости достижений. → Проверка: ответ API совпадает с контрольной выгрузкой и не подменяет роль максимальным `rang` за всю историю.
- [ ] Добавить типизированный клиент нового API, Zustand-состояние с loading/error и загрузку одной согласованной модели профиля; удалить из production-пути `mockCareerAchievements` и зависимость карьерного блока от achievement endpoint-а. → Проверка: production build не использует mock и запросы в DevTools идут только на `/user/career/:username`.
- [ ] Доработать блок «Карьера» в `UserPage26`: актуальная запись сверху и раскрыта по умолчанию, прошлые сворачиваются; заголовок показывает роль, отдел, главу и год; тело — отдел, бригаду, «Должность 1…N», новые и прежние навыки, пустое состояние. → Проверка: mobile и desktop соответствуют обоим макетам для нескольких периодов и двух должностей в одном периоде.
- [ ] Реализовать «Дерево прокачки сотрудника»: отдельный маршрут или модальное представление использует тот же карьерный API и связывает периоды хронологически; «Дерево корпорации» ведёт на согласованный корпоративный маршрут либо скрыто до реализации. → Проверка: кнопки не являются заглушками, доступны с клавиатуры и позволяют вернуться в кабинет.
- [ ] Подключить read-only историю к публичному профилю, если это входит в продуктовую область; иначе зафиксировать ограничение личным кабинетом и не выполнять лишние запросы. → Проверка: e2e-тест фиксирует утверждённый вариант для `/user/:username` и `/profile/:username`.
- [ ] Накатить на staging, сверить отчёт импорта и API для контрольных пользователей, затем провести production rollout с резервной копией. В конце прогнать миграционные, API-контрактные, frontend-компонентные и e2e-тесты. → Проверка: CI зелёный, `ya-yara` одобрила PR, а карточки контрольных пользователей совпадают с утверждёнными исходными данными.

## Готово, когда

- [ ] Backend сохраняет и выдаёт карьерную историю, а административные операции не могут испортить хронологию.
- [ ] Личный кабинет работает как в макете на desktop и mobile, включая дерево прокачки и пустые/ошибочные состояния.
- [ ] Импорт воспроизводим: исходная выгрузка, отчёт валидации и результат миграции можно сверить построчно.

## Примечание

Критический путь: сначала утверждение исходных данных и схема БД, затем импорт и API, после этого frontend. `useroles` можно оставить как совместимый список назначенных ролей, а `user.role` — как быстрый указатель текущей основной должности.
